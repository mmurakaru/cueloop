# VCS adapters and extension loading: prior art

## Question

Which boundaries are useful when cueloop adds native Git, Jujutsu, and later Sapling diff sources, and leaves room for third-party sources and UI contributions? This note records verified behavior in the current Hunk and pi sources. It is evidence for a design discussion, not a decision to copy either API.

Research checked 2026-09-26. Upstream `main` links can move; pin commit URLs before turning these observations into an implementation spec.

## Hunk's current VCS contract

- The public `registerVcsAdapter` contract has `detect`, optional operations for working-tree diff, revision show, and stash show, plus optional history. A missing operation produces an unsupported-command error. [Source type](https://github.com/modem-dev/hunk/blob/main/packages/hunk/src/extension-api/types.ts), [adapter guide](https://www.hunk.dev/docs/extend/vcs-adapters/).
- An operation returns repo root, labels, and a Git-format patch. It may also return untracked paths, separately described or skipped files, an exact old/new file reader, and a source cache key. The exact reader must pin its revision before returning so later reads cannot silently move with a ref. [Source type](https://github.com/modem-dev/hunk/blob/main/packages/hunk/src/extension-api/types.ts), [adapter guide](https://www.hunk.dev/docs/extend/vcs-adapters/#exact-file-sources).
- Detection chooses the nearest checkout first, then uses priority for colocated markers at the same root. Bundled jj wins over Sapling and Git at that root; an explicit `vcs` config wins over detection. A third-party adapter starts below Git to avoid changing an existing checkout merely by being installed. [Adapter guide](https://www.hunk.dev/docs/extend/vcs-adapters/#detection-order).
- A watch operation can supply a fingerprint and an event target plan. Without a plan Hunk polls the fingerprint. Its jj and Sapling watch workflows currently poll. [Source type](https://github.com/modem-dev/hunk/blob/main/packages/hunk/src/extension-api/types.ts), [workflow guide](https://www.hunk.dev/docs/workflows/jujutsu-and-sapling/).
- Hunk accepts native jj and Sapling revsets, supports two-revision comparisons, and exposes public VCS registration. [Workflow guide](https://www.hunk.dev/docs/workflows/jujutsu-and-sapling/), [changelog](https://github.com/modem-dev/hunk/blob/main/CHANGELOG.md), [adapter guide](https://www.hunk.dev/docs/extend/vcs-adapters/).

## Hunk's extension boundary

- Bundled Git, jj, Sapling, and UI extensions register through the public API; bundled providers load before config resolution, while user extensions load during app startup. Registration is collected and applied through a registry; a failed factory rolls its registrations back. [Architecture](https://github.com/modem-dev/hunk/blob/main/docs/extension-architecture.md).
- User sources include explicit CLI paths, user config paths, a user extension directory, and repository files. Repository code waits for an explicit trust decision. `--no-extensions` disables user code while bundled providers remain. Extension code still runs with the user's operating-system permissions. [Extension guide](https://www.hunk.dev/docs/extend/extensions/#where-hunk-looks), [trust guide](https://www.hunk.dev/docs/extend/extensions/#trust).
- Public contributions already include panes on four terminal edges, file views, keyboard modes, commands, changeset transforms, lifecycle events, and VCS adapters. The extension API is explicitly experimental and versioned. Menu entries, standalone keybindings, custom note renderers, and session commands are listed as unavailable. [Extension API](https://www.hunk.dev/docs/extend/extension-api/), [pane guide](https://www.hunk.dev/docs/extend/custom-sidebars/).
- The host retains authority over review documents, note placement, scrolling, and validated file-view geometry. A custom pane receives frozen review facts and guarded actions; a custom file view paints within host-validated rectangles. This is a useful precedent for keeping annotation meaning independent of extension rendering. [Architecture](https://github.com/modem-dev/hunk/blob/main/docs/extension-architecture.md).

## Pi's extension lifecycle

- Pi discovers user and project extension files and also accepts an explicit `--extension` path. A default-exported factory receives a typed API, and TypeScript loads without a separate build. Extensions run in the Pi process with the user's permissions. [Extension guide](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md).
- The loader stages registrations during an async factory. On success it commits them; on failure it discards them. Runtime operations are unavailable after a failed load. This makes partial registration a defined case rather than a corrupted session. [Loader source](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/extensions/loader.ts).
- Pi recommends creating watchers, sockets, and processes at session start rather than during factory loading, then closing them in an idempotent shutdown handler. Reload replaces the extension runtime; code after reload must not use captured old runtime state. [Extension guide](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md#respect-the-runtime-lifecycle).
- Registration covers tools, commands, event hooks, message renderers, and UI components. Terminal-only components are unavailable in noninteractive modes; RPC can forward supported dialogs and notifications. Event handlers have ordered dispatch and documented error behavior, including fail-safe blocking for a failed tool gate. [Extension guide](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md#follow-the-extension-contracts), [loader source](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/extensions/loader.ts).

## Design implications to test in cueloop

1. Keep VCS selection and diff capture in the daemon. Let an adapter describe a source request and return one pinned review snapshot: immutable patch, source identity, exact old/new content when available, and an explicit status for unavailable content. The schema should hold serializable facts, never an adapter callback. This follows from Hunk's pinned reader requirement and cueloop's daemon-owned session mutation. [Hunk adapter guide](https://www.hunk.dev/docs/extend/vcs-adapters/#exact-file-sources).
2. Separate a source's **continuity identity** from the **reviewed snapshot identity**. For jj, a change ID can identify the logical change through rewrites; its commit ID and content digest identify exactly what a person reviewed. If continuation is ambiguous, require an explicit selection. This is a proposed cueloop rule, not a claim that Hunk lacks internal snapshot identity. Hunk's file model already distinguishes content and source identities. [Hunk review architecture](https://github.com/modem-dev/hunk/blob/main/AGENTS.md).
3. Keep refresh as a host action. An adapter may report that its source moved, but it must not replace a pinned Thread revision or relocate annotations by itself. Reuse the current refresh control and record a new revision only when refresh is invoked for pinned reviews. Working-copy hot reload can retain its current behavior. This is a proposed cueloop behavior.
4. Put first-party Git and jj through the same narrow source contract offered to third parties. Public registration should be versioned and capability-based, with explicit unsupported operations and namespaced IDs. Defer UI contributions until the host can expose read-only review facts and guarded actions without giving extensions daemon/session mutation. Hunk's architecture shows why host ownership of review semantics matters; pi's loader shows how to stage registrations and clean up failed loads. [Hunk architecture](https://github.com/modem-dev/hunk/blob/main/docs/extension-architecture.md), [Pi loader](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/extensions/loader.ts).
5. Treat repository-local executable extensions as a separate trust decision from selecting a built-in VCS adapter. An adapter's metadata and config may be read without executing project code. Any future user extension should have a disable switch, attributed errors, lifecycle cleanup, and clear behavior in headless modes. [Hunk trust guide](https://www.hunk.dev/docs/extend/extensions/#trust), [Pi extension guide](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md).

## Limits of this review

The cited Hunk docs describe live review snapshots and notes, but do not establish whether one persistent review conversation follows a rewritten jj change across multiple submitted revisions. A focused source inspection or behavioral test is needed before treating that as a verified limitation. Cueloop's Thread invariant is independent of that question: every annotation must remain tied to the exact reviewed text or be marked unresolved.
