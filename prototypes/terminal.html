Implementation Plan: Session Persistence

cueloop keeps every review session in daemon memory today. If the daemon crashes mid-review — or the machine reboots — the human's pending annotations and the agent's submitted plan are gone, and the agent is left waiting on a verdict that will never arrive. This plan persists sessions to disk so a restarted daemon can pick up exactly where the review left off.

Phase 1: Storage layer

Introduce a small storage layer that owns serialization and atomic writes. Nothing above this layer should know about the filesystem. Three new files, all under server/storage/:

  • -server/storage/store.ts — persistSession / loadSession with atomic temp-file-then-rename writes
  • -server/storage/recover.ts — boot-time scan that rebuilds in-memory sessions from disk
  • -server/storage/types.ts — the persisted record schema, versioned from day one

Every session serializes to a single versioned record. Anything the review loop needs to resume lives here:

interface SessionRecord {
  id: string;
  schemaVersion: string;
  artifact: Artifact;
  annotations: Annotation[];
  verdict: Verdict | null;
}

Phase 2: Recovery on boot

On startup the daemon replays whatever survived. Recovery has to be safe to run against a half-written directory — a crash can happen mid-persist, so partial files are expected, not exceptional.

  1. 1.Scan .cueloop/sessions/ and parse every *.json record, skipping any whose schemaVersion is unknown.
  2. 2.Rehydrate every record with a null verdict into the active review queue, then notify the connected agent that its session is live again.
  3. 3.Move records that fail to parse into sessions/quarantine/ instead of deleting them, and log one warning per file.

Open questions

  • -Should completed sessions be pruned after a retention window, or kept indefinitely as an audit log?
  • -Is one JSON file per session enough, or do we need an append-only log once annotation volume grows?
