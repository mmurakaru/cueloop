Implementation Plan: Session Persistence

submitted by agent builder-7 · awaiting your review

Context

cueloop currently keeps every review session in memory. If the daemon crashes or the machine reboots mid-review, the human’s annotations and the agent’s pending plan are simply gone, and the agent is left waiting on a verdict that will never arrive. This plan introduces a small write-ahead storage layer so that any in-flight session can be recovered exactly as it was.

Phase 1: Storage layer

All persistence lives in a new server/storage/ directory. Sessions are serialized to JSON, one file per session, written atomically via a temp-file rename so a partial write can never corrupt an existing record. No database, no migrations — the filesystem is the store.

  • server/storage/store.ts — read, write, and list operations for session records, with an in-process write queue so concurrent flushes never interleave.
  • server/storage/schema.ts — the SessionRecord type and a SCHEMA_VERSION constant, bumped on any breaking shape change.
  • server/storage/index.ts — the public API surface; nothing outside this directory imports store internals.
interface SessionRecord {
  id: string;
  schemaVersion: string;
  artifact: Artifact;
  annotations: Annotation[];
  verdict: Verdict | null;
}

Phase 2: Recovery on boot

On startup the daemon scans the storage directory before accepting any new connections. Recovery is strictly read-only until the scan completes, and a session that fails to parse is quarantined rather than deleted.

  1. Enumerate *.session.json files and parse each one, validating schemaVersion against the current constant.
  2. Rehydrate valid records into the in-memory session table and mark them as recovered so the UI can surface a banner.
  3. Notify any reconnecting agent whose session survived, replaying the last known state so it can resume waiting for a verdict.

Open questions

  • Should recovered sessions expire after a TTL, or wait indefinitely for the human to return?
  • Is one file per session durable enough, or do we need an append-only journal so individual annotations survive a crash too?
