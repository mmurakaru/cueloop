Implementation Plan: Session Persistence

Review sessions currently live only in daemon memory. If the daemon crashes or the machine reboots mid-review, every pending annotation is lost and the agent is left waiting on a verdict that will never arrive. This plan persists session state to disk after every mutation, so a restarted daemon can pick up exactly where the reviewer left off.

needs work
Phase 1

Storage layer

Introduce a storage layer that owns serialization, atomic writes, and schema versioning. All writes go through a single write-then-rename path, so a crash mid-write can never corrupt an existing session file. Nothing outside this layer touches the filesystem.

needs work

Three new files under server/storage/:

  • store.ts — SessionStore class exposing load, save, and delete, with atomic temp-file rename writes
  • schema.ts — the SessionRecord type, the schemaVersion constant, and record validators
  • migrate.ts — forward migrations that upgrade older on-disk records at read time

Phase 2

Recovery on boot

On boot the daemon scans the sessions directory before accepting any connections. Recovery is best-effort by design: an unreadable record is quarantined rather than deleted, and boot always continues. A corrupt file should never take the daemon down with it.

needs work
  1. Scan ~/.cueloop/sessions for *.json and parse each record found
  2. Validate schemaVersion, run forward migrations, and move files that fail validation into .quarantine/
  3. Re-register recovered sessions with the review router and notify any waiting agent connections
needs work

Open questions

  • Should verdicts that were already submitted be replayed to agents that reconnect, or dropped after an acknowledgement window?
  • Is one file per session enough, or do we need a compaction step once annotation counts grow large?
