Implementation Plan: Session Persistence

submitted by agent/worker-3 · rev 1 · awaiting review

cueloop keeps every review session in daemon memory today. If the daemon crashes or restarts mid-review, the artifact, its annotations, and any draft verdict are gone, and the agent is left waiting on a review that no longer exists. This plan introduces a small storage layer that persists each session to disk as it changes, so a restarted daemon can pick up exactly where it left off.

Phase 1: Storage layer

All persistence lives in a new server/storage/ module. Sessions are written as one JSON document per session, keyed by session id. Writes go through a temp file and an atomic rename, so a crash mid-write can never leave a corrupt record behind.

  • server/storage/schema.ts — the SessionRecord shape and the current SCHEMA_VERSION constant.
  • server/storage/store.ts — read, write, and list operations, with atomic writes and corruption recovery.
  • server/storage/index.ts — the public surface the daemon imports; nothing else reaches into this directory.
interface SessionRecord {
  id: string;
  schemaVersion: string;
  artifact: Artifact;
  annotations: Annotation[];
  verdict: Verdict | null;
}

Phase 2: Recovery on boot

On boot, the daemon scans the storage directory before it accepts any connections. Recovery is strictly read-only: nothing is deleted or rewritten until a client reattaches to the session.

  1. Scan server/storage/data/ for *.json records and parse each one, skipping — and logging — any file that fails validation.
  2. Rebuild the in-memory session table from the surviving records, marking each restored session as recovered.
  3. Notify any reconnecting agent that its session survived, including the count of annotations already recorded against it.

Open questions

  • Should recovered sessions expire after some TTL, or wait indefinitely for the reviewer to come back?
  • Is one JSON file per session enough, or do we want an append-only log for the annotation history?
